Kunwei 软件产品组合评审：与 VALD 等国际竞品对齐
本次评审的核心不是简单判断 KWinHub、KWinPerformance、KWinScience 和 KWinCore 是否都应该存在，而是明确它们之间的产品边界、数据归属、技术职责和交付成熟度，避免四个产品重复建设数据模型、计算逻辑、用户管理和设备接入能力。

我综合了项目中的《海外竞品与方案对比》《Explain KWinHub APIs》和《竞品分析报告》三份材料。以下会严格区分：
- 已交付事实：现有材料能够支持的代码、原型或既有技术基础，不等于已正式商用。
- 开发中／待验证能力：材料显示已有实现基础，但不能证明已经生产可用；若没有明确进度证据，会标为“状态待核实”。
- 规划建议：为统一技术架构和缩小与竞品能力差距而提出的目标设计，不代表 Kunwei 已经实现。
一、核心结论
建议将 Kunwei 规划为“一个数据平台、一个科学计算引擎、多个业务应用、一套共享技术基础”。
KWinHub — 统一数据与业务平台

组织、用户、运动员、测试记录、历史趋势、权限、报告、外部 API


KWinPerformance

测试执行、设备控制、实时反馈、专项分析与工作流


KWinScience

指标定义、算法、协议、计算版本、科学结果可追溯性




KWinCore — 共享技术基础

通用领域契约、身份与组织上下文、数据访问规范、日志、版本与集成组件


桌面端 · 移动端 · Web · 设备与传感器

力台、测力起跑器、计时设备、高速摄像机及其他数据源


这是建议的逻辑架构，不是对现有代码部署拓扑的描述。实际系统可以先采用模块化单体，不需要为了匹配该图就立即拆分微服务。

这个方向与竞品材料的主要结论一致：VALD 的优势不只是单台设备的测量能力，而是把设备、运动员档案、测试结果、历史数据和报告连接起来。Hawkin Dynamics 更适合对标力台测试、标准化协议和自动化计算；Kinvent 可用于对标多类型传感器及测试数据整合；MuscleLab 和 Brower 则对专项测试、速度与计时工作流有参考价值。

Kunwei 的机会，是把自身设备和专项测试能力连接成统一数据体系，而不是让每个客户端都发展成一个独立、互不兼容的软件系统。

成熟度判断需要注意什么
当前能相对明确判断的是：KWinHub 有可检查的 MVP 技术基础，但不能据此认定已经具备生产级 SaaS 能力。 对另外三个产品，现有资料主要支持其产品方向或架构定位，不足以确认每项能力究竟已经交付、正在开发，还是仅处于规划阶段。

因此，不建议直接给四个产品都标注“已交付”或“开发中”。最好建立一张内部的能力台账，以实际版本、部署环境、用户使用情况和验收证据作为状态依据。
三、对标 VALD 等竞品：差距应该落在哪些层面？
竞品不是要逐个复制的功能清单。建议从端到端能力链条比较。
能力层	主要竞品参考	Kunwei 应达到的目标	建议优先级
身份、组织与运动员档案	VALD Hub、Kinvent	统一身份、组织隔离、队伍与运动员关系；不同客户端使用同一运动员身份	P0
设备接入与数据同步	VALD、Hawkin、MuscleLab	客户端能够安全提交测试会话、试次、结果和文件引用；失败可重试、状态可追踪	P0
专项测试流程	Hawkin、MuscleLab、Brower	各专项应用保留专业性，但共享身份、数据契约和基础能力	P0
科学计算与指标标准化	VALD、Hawkin、MuscleLab	指标定义、单位、计算方法、算法版本与历史结果可追溯	P0–P1
纵向趋势、团队分析和报告	VALD Hub、Kinvent、Output	以统一数据为基础查询历史、比较群组、生成报告	P1
视频与多设备同步	VALD ForceDecks Vision 等相关方案	将力信号、计时事件、视频和测试结果关联到同一个测试过程	P1，先验证试点需求
规范数据库、复杂分析与外部生态	VALD 等平台	先验证客户价值，再投入规范值、第三方系统深度集成等建设	P2
P0 表示基础交付门槛；P1 表示在真实数据闭环稳定后扩展；P2 表示更适合在需求验证后投入。这里的优先级是 Kunwei 的建议，并非竞品自身的产品开发顺序。

最重要的差距不是页面数量，而是数据能否跨应用一致地流动。 如果一个运动员在起跑测力客户端和跳跃测试客户端里出现两份独立档案，或者同名指标由不同程序用不同算法计算，那么即使 Hub 已经有仪表盘，也还没有形成真正统一的平台。
四、建议统一的数据架构
4.1 建立统一领域模型
建议先把下列对象的含义、主键、关系和数据归属统一下来。
组织与身份域

Organization · User · OrganizationMembership · Role · Team · Athlete

解决数据归属、组织隔离、团队关系和跨客户端身份一致性。

测试业务域

TestProtocol · MeasurementSession · SessionDevice · Trial

一个测试会话应能关联一个或多个设备及多个试次，而不是被单个 DeviceId 限制。

科学结果域

MetricDefinition · Result · ResultMetricValue · AlgorithmVersion

指标定义和实际测量值分离；记录单位、计算版本、输入来源与质量信息。

数据资产与处理域

DataSource · Device · DataObject · ProcessingJob · SyncStatus

管理原始文件、视频、上传状态、处理任务和可追踪的数据来源。


这与 KWinHub 代码评审提出的方向一致：当前 MeasurementSession 的单设备关联可能限制多设备场景；当前结果指标模型需要区分可复用的指标定义和具体结果值；算法版本与协议版本需要从简单字符串逐步发展为可追溯的版本化定义。

4.2 明确数据由谁负责
数据类别	建议的权威归属	客户端可以做什么
用户、组织、角色和运动员主档	KWinHub	查询；通过授权 API 创建或更新
设备连接状态、实时采集缓冲区	设备接入层或 KWinPerformance	连接设备、采集、缓存、显示状态
测试会话、试次及设备关联	KWinHub 的统一数据模型	发起测试并提交会话数据
原始信号、视频和大文件	私有对象存储；KWinHub 保存元数据与引用	上传文件、获取经授权的访问链接
指标定义与算法版本	KWinScience 的规范化定义	调用统一计算能力，展示结果
测量结果与历史记录	KWinHub 统一管理	查询、展示、比较和导出
本地缓存和离线队列	各桌面／移动客户端	暂存待同步数据，不成为跨客户端的权威数据源
建议保留一个重要原则：Hub 是统一记录与业务查询的中心，但不必承担所有实时采集和高频信号处理工作。

例如，桌面端需要以高采样率接收测力台信号时，可以先在本地完成采集和必要的实时计算，再把原始数据或文件引用、测试元数据和结果可靠地同步到 Hub。这样既避免网络波动影响现场测试，也能让其他客户端查看统一历史记录。
五、桌面、移动端和 Web 的集成方式
建议采用统一 API，而不是让每种客户端分别连接数据库或共享内部服务实现。
桌面端

设备采集、实时处理、离线缓存


移动端

现场测试、轻量采集、结果查看


Web

管理、分析、趋势与报告



KWinHub API

身份认证 · 组织授权 · 数据提交 · 查询 · 同步状态 · 文件访问

统一领域模型与服务

业务数据库 · 对象存储 · 计算任务 · 审计日志


建议先落实以下接口约定：
1. 身份认证：桌面和移动端采用适合公共客户端的 OAuth 2.0 / OIDC 授权流程，例如 Authorization Code + PKCE；不要在分发给客户的客户端内嵌长期保密密钥。
2. 数据提交：提供版本化 API；每次上传携带稳定的会话／试次标识和幂等键，避免重试导致重复记录。
3. 同步状态：提供任务状态查询、错误原因和可重试机制。Heartbeat 适合报告客户端在线状态，不能替代数据上传。
4. 大文件上传：原始信号和视频优先使用受控的对象存储上传流程，数据库记录文件元数据、校验值和授权关系。
5. 离线能力：客户端使用本地队列暂存数据，恢复网络后重试，并能区分待上传、上传中、已接收、处理失败和已完成。
6. 数据版本：API 契约、指标定义和算法版本都需要明确版本策略，避免一个客户端升级后悄悄改变其他产品的结果含义。
六、KWinScience 和 KWinCore 应如何分工？
这两个名称最容易发生职责重叠，建议在正式 PRD 和代码仓库中分别定义。
维度	KWinScience	KWinCore
核心问题	“如何科学地计算和解释测试结果？”	“不同产品如何用一致、安全的方式协作？”
主要内容	指标定义、算法、协议、计算参数、版本、结果溯源	公共契约、身份上下文、通用组件、API 规范、日志和集成机制
示例	跳跃高度算法、峰值力、左右不对称率、起跑阶段分析	统一的 Athlete ID、会话 ID、错误模型、数据提交 DTO
不应负责	用户管理、Hub 页面、所有业务流程	业务指标的科学定义、专项测试流程
验收标准	相同输入和版本可复现结果；历史结果可追溯	产品之间共享契约稳定；升级不会无意破坏其他客户端
如果某项指标需要不同产品使用，应由 KWinScience 定义其计算语义，KWinCore 提供必要的调用契约或公共类型，而 KWinHub 保存计算结果及来源。

初期可以把它们实现为同一个 .NET 解决方案内的独立模块或类库。只有在存在独立部署、计算负载隔离、跨语言复用或明确的运维需求时，再考虑把 KWinScience 拆成独立服务。
七、建议的实施顺序
1. 阶段 1：核实现状，冻结公共契约
   
   交付物：四个产品的真实状态清单、仓库和部署映射、数据模型图、接口清单、统一身份与会话契约。
   
   验收重点：能说清每个数据对象由谁维护、谁能修改、哪些客户端正在使用。
2. 阶段 2：补齐 KWinHub 生产基础
   
   交付物：真实认证与租户隔离、统一运动员档案、测试会话与试次、真实数据 API、同步状态、自动化集成测试。
   
   验收重点：未授权用户无法访问其他组织的数据；重复上传不会重复创建结果；失败数据可以恢复。
3. 阶段 3：选一个专项应用打通全链路
   
   选择一条具有真实设备、明确客户场景和稳定算法的测试流程，例如测力台跳跃测试或起跑测力测试。
   
   验收重点：从设备采集、客户端处理、上传、Hub 保存到历史查询和报告，整条链路都使用真实数据。
4. 阶段 4：抽取共享科学能力
   
   把已验证、确实需要跨应用复用的指标与算法纳入 KWinScience；把稳定的公共契约和组件归入 KWinCore。
   
   验收重点：第二个客户端可以复用既有能力，而不需要复制业务模型或重新实现同一指标。
5. 阶段 5：扩展平台化能力
   
   在基础链路稳定后，再投入多设备联合测试、视频同步、群组仪表盘、规范值、复杂报告和外部系统集成。
   
   验收重点：这些能力解决了真实用户需求，并且不会破坏既有历史数据和计算结果。
八、建议下一步形成一张“真实能力与交付状态矩阵”
当前材料足以提出目标架构，但还不足以把所有代码、客户端和功能准确地归入已交付、开发中或规划中。建议把下面这张矩阵作为下一轮工程核查的正式输出。
核查对象	必须收集的证据	状态判断依据
KWinHub	部署版本、认证配置、真实 API、数据库迁移、集成测试、生产使用情况	能否安全、稳定地支撑真实用户与真实数据
KWinPerformance	每个客户端及专项模块的版本、设备支持列表、实际数据出口、验收记录	是演示原型、可用客户端，还是正式交付产品
KWinScience	算法仓库、调用方、指标定义、版本机制、计算验证数据	是否已跨产品复用，并且能够复现历史结果
KWinCore	公共包／项目清单、依赖图、版本发布流程、契约兼容性测试	是否存在真实复用，而非仅有架构命名
跨产品数据链路	同一运动员在两个客户端的完整测试记录、失败重试记录和查询结果	是否真正做到跨应用共享身份、数据与历史
我的最终建议是：先把 KWinHub 定位为统一数据平台，把 KWinScience 定位为科学计算能力层，把 KWinCore 定位为共享技术基础，并让 KWinPerformance 专注专项测试体验。 然后通过一个真实测试场景验证这套分工，再逐步扩展到更多设备和客户端。

这样既与 VALD 等平台型竞品的方向一致，也能降低 Kunwei 在桌面、移动端和 Web 多端并行开发时产生的数据割裂、算法重复和维护成本。
