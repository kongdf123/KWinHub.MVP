# KWinHub navigation and main-layout review

My recommendation is to simplify the navigation in `KWinHub.Web.React` and `KWinHub.PlatformConsole`, while keeping them as two distinct applications with different purposes.

I reviewed the available business analysis and VALD competitor research, along with the current sidebar and layout code in the [KWinHub.MVP repository](https://github.com/kongdf123/KWinHub.MVP?utm_source=chatgpt.com).

Your intuition is sound: KWinHub should feel like a professional sports-performance SaaS platform, not a collection of independent tools or an internal developer console. The navigation should reflect how coaches, sports scientists, and platform administrators work—not simply mirror the backend's entities or the development team's project structure.

There is one important distinction, though: single-level navigation does not mean every page should be a top-level menu item. It means each primary navigation item should lead directly to a useful destination, without requiring users to expand nested menus or guess where a feature lives.

## 1. What I found in the current implementation

`KWinHub.Web.React` — the customer-facing Hub

Simplify

The current sidebar has five collapsible groups, plus Overview, and approximately 20 navigation destinations. It exposes athletes, teams, sessions, protocols, devices, synchronization, results, performance, trends, comparisons, biomechanics, dashboards, reports, datasets, raw data, data sources, integrations, and administration.

Several of these are different views of the same workflow and probably do not all deserve permanent top-level navigation.

`KWinHub.PlatformConsole` — the internal platform administration app

Retain separate purpose

Its current sidebar has four groups: Overview, Tenants, Catalogs, and Security. The destinations cover the dashboard, organizations, users, protocol catalog, metric catalog, device catalog, algorithm versions, and audit logs.

This is already substantially simpler. I would flatten the sidebar into direct links and reserve the console for platform-wide governance and administration.

These observations come from the current navigation definitions and layout components. The proposed changes below are product-design recommendations; I have not modified the repository.

The business analysis also supports this direction: KWinHub's core value is the connection between athlete identities, multi-device testing, scientific results, longitudinal analysis, and reporting—not the number of separate pages it offers.&#x20;

### How I would consolidate the existing features

| Current features                                                    | Recommended destination                           | Treatment                                                                      |
| ------------------------------------------------------------------- | ------------------------------------------------- | ------------------------------------------------------------------------------ |
| Overview                                                            | Overview                                          | Keep as the landing page                                                       |
| Athletes, Teams                                                     | Athletes                                          | Integrate teams and groups into the athlete-management experience              |
| Sessions, Protocols, Devices, Sync Center                           | Testing                                           | Consolidate the testing workflow; keep each as a direct page or contextual tab |
| Results, Performance, Trends, Comparisons, Biomechanics, Dashboards | Analysis                                          | One analysis workspace with contextual views                                   |
| Reports                                                             | Reports                                           | Keep as a first-class destination                                              |
| Datasets, Raw Data                                                  | Testing details or data inspection                | Move to session details or advanced inspection views                           |
| Data Sources, Integrations, Sync Center                             | Data & Integrations                               | Consolidate integration configuration and synchronization monitoring           |
| Organization, Users, Roles, Settings                                | Settings                                          | Consolidate administrative settings                                            |
| Device management                                                   | Testing, with administration controls in Settings | Avoid two competing destinations for the same device records                   |

There are a few nuances worth preserving.

Athletes and Teams: I would not discard Teams as a capability. Team management is essential in sports performance, but it can be integrated into the athlete workspace. Users can access team lists, group membership, and team-level analysis without a separate permanent menu item.

Testing and Protocols: Protocols are reusable test definitions; sessions are actual testing events. They are different concepts, but they belong to the same testing workflow. A user should be able to select a protocol when starting a test and inspect the protocol from the relevant session without navigating through a complex hierarchy.

Analysis: Results, trends, comparisons, and biomechanics are closely related, but not necessarily the same page. I would make Analysis the main destination, with a clear set of contextual views or tabs inside it. A sports scientist should be able to move from an individual result to a historical trend or a team comparison without losing the selected athlete, session, or filters.

Data & Integrations: This deserves its own destination because automatic ingestion, synchronization status, and external API connections are central to KWinHub's value proposition. However, raw files and technical datasets should not compete with athlete management and analysis for prominent sidebar space.

The objective is to simplify the navigation without removing useful capabilities.

## 3. What should happen to the two-level sidebar?

I recommend removing expandable navigation groups, but retaining grouping within pages where it improves usability.

| Navigation pattern                                               | Recommendation                   |
| ---------------------------------------------------------------- | -------------------------------- |
| Expandable sidebar groups such as PEOPLE, TESTING, and ANALYSIS  | Remove                           |
| Direct links to primary destinations                             | Use                              |
| Tabs within a workspace, such as Results / Trends / Comparisons  | Use when the views share context |
| Tabs or sections on an athlete profile                           | Keep                             |
| Contextual actions within a session, such as inspecting raw data | Keep                             |
| Breadcrumbs on deeply nested detail pages                        | Keep where useful                |
| Collapsible sidebar width                                        | Keep                             |
| Role-based visibility of navigation items                        | Keep                             |

For example, navigating to an athlete should open the athlete profile directly. Within that profile, users might see tabs such as Overview, Testing History, Trends, and Reports. Those tabs are contextual navigation, not a second layer of global sidebar menus.

Likewise, clicking a session should open its detail page, where the user can inspect results, associated devices, raw data, and processing status.

This structure gives users fewer decisions to make on every screen while preserving access to the full feature set.

## 4. Recommended navigation for KWinHub.PlatformConsole

The Platform Console has a different audience. It is for internal platform operators and authorized administrators, not everyday coaches or sports scientists.

I would keep it separate from the customer-facing Hub and use a flat navigation structure with five destinations:

Overview

Platform health, organization counts, recent activity and operational alerts.

Organizations

Tenant lifecycle, organization details, membership and organization-level administration.

Users

Platform accounts, access status and authorized administrative actions.

Scientific Catalogs

Protocols, metric definitions, device definitions and algorithm versions.

Security & Audit

Audit records, privileged actions and security-related investigations.

The existing routes can remain unchanged:

- `/` — Overview
- `/organizations` — Organizations
- `/users` — Users
- `/catalogs/protocols`, `/catalogs/metrics`, `/catalogs/devices`, `/catalogs/algorithms` — Scientific Catalogs
- `/audit-logs` — Security & Audit

The four catalog routes can become tabs on a single catalog landing page, or a catalog page with an internal selector. I would choose tabs if each catalog has comparable importance and similar interaction patterns; otherwise, use a compact catalog index.

One architectural distinction matters here: the Platform Console should manage global definitions and platform governance, while the customer-facing Hub should manage organization-level work and athlete data. For example, editing a globally supported protocol definition belongs in the console, while selecting a protocol for a testing session belongs in the Hub.

Authorization must enforce this separation on the backend. Hiding a sidebar item is not a security boundary.

### Specific changes I would make to the current code

In both applications, the current layout already includes useful foundations: collapsible sidebar width, scrollable navigation, active-route styling, and keyboard focus indicators. I would preserve those rather than rewrite the entire shell.

I would prioritize the following refinements:

1. Remove the group-collapse state and logic from the primary sidebar. The active route should still highlight the correct destination, including detail pages.
2. Add a consistent top header with page title, organization context where applicable, and account controls.
3. Use consistent spacing and component styles across both applications while retaining their distinct branding and access boundaries.
4. Support responsive layouts. On smaller screens, use an accessible drawer instead of forcing the desktop sidebar into a narrow viewport.
5. Keep navigation role-aware. Only show links the current user is permitted to access, and enforce the same permissions in the API.
6. Use clear loading, empty, error, and synchronization states. These are especially important in a platform that receives data from external devices and desktop applications.
7. Avoid adding technical implementation details to the customer-facing sidebar. Raw-data inspection and processing diagnostics should appear in the relevant session or administrative context.

### A. Flatten the Hub sidebar

### C. Make advanced session tabs permission-aware

File: [`src/frontend/KWinHub.Web.React/src/pages/SessionDetailPage.tsx`](https://github.com/kongdf123/KWinHub.MVP/blob/main/src/frontend/KWinHub.Web.React/src/pages/SessionDetailPage.tsx?utm_source=chatgpt.com)

The session detail page already has contextual tabs for Raw Data, Processing, and Data Quality. This is the right place for those capabilities, but the current `TABS` array includes them unconditionally.

The existing app permission model already distinguishes roles. For example, the `coach` role does not include `raw-data`, while `org-admin` and `support` do. Reuse that model rather than inventing a separate UI-only role system.

Change the context access:

```
const { viewParams, navigate, addToast, lang, canAccess } = useApp();
```

Then derive the visible tabs:

```
const advancedTabKeys = new Set<Tab>([
  'rawData',
  'processing',
  'dataQuality',
]);

const visibleTabs = TABS.filter(
  (item) =>
    !advancedTabKeys.has(item.key) ||
    canAccess('raw-data'),
);
```

Use `visibleTabs` wherever the component renders its tab buttons, instead of mapping directly over `TABS`.

This is a navigation visibility change, not a complete security boundary. The API must also authorize access to raw measurements, diagnostic details, and exports. If the backend does not enforce these permissions yet, that should be a release-blocking follow-up.

For the same reason, any navigation links to datasets, raw data, or ingestion diagnostics elsewhere in the Hub should use the same permission model. Do not rely solely on hiding sidebar entries.

## 3. Layout improvements beyond navigation

I would keep the visual redesign focused. The repository already has Tailwind, Lucide icons, CSS theme tokens, focus indicators, and compact navigation support.

Responsive navigation

On desktop, keep the current collapsible sidebar. On small screens, use a drawer with an explicit open/close control; do not let a fixed-width sidebar consume most of the viewport. The Hub currently renders its sidebar as a sticky, full-height element, so this needs an additional responsive pass.

Consistent page headers

Standardize page title, short description, primary action, and optional breadcrumb. The Console already has a header with a title; the Hub would benefit from a more consistent page-level header contract.

Clear permission boundaries

Hide unauthorized navigation and tabs, handle unauthorized direct navigation, and enforce access in the backend. The current Hub `AppContent` switch renders views based on `currentView`; sidebar filtering alone does not prevent a view from being selected by another route or action.

Session diagnostics

Keep processing lifecycle, data quality, raw measurements, and ingestion troubleshooting inside the session. Present status and user-actionable errors first; expose low-level details only to authorized roles.

## 3. Three design rules I would establish

Rule 1 — Sidebar means product area

Keep approximately 6–8 primary items, each with a clear business meaning. Avoid putting individual metrics, technical tools, or every page route into the sidebar.

Rule 2 — Tabs mean sections of the selected area

Put tabs below the page title and above the page content. Preserve the selected tab when practical, and make the active tab visually obvious. Do not put unrelated workflows into the same tab group just to reduce the sidebar.

Rule 3 — Detail pages have contextual navigation

Selecting a session or athlete should open its detail view with its own relevant tabs. Do not duplicate all those tabs in the global sidebar.

## 4. Important implementation detail

I recommend retaining the existing React routes rather than replacing the routing system. The sidebar changes the primary area; a route-aware tab bar changes the selected section. For example, `/catalogs/protocols` and `/catalogs/metrics` can remain valid routes while sharing the Scientific Catalogs shell.

That distinction matters: a tab should navigate to a real route, not merely swap local component state, especially when users need browser Back/Forward, deep links, refresh persistence, and access control.

My recommendation is to implement this shared navigation pattern in both applications, with different primary areas appropriate to each audience. One remaining design decision is whether selecting a primary item should open its default tab immediately or remember the last-used tab for that area. I would default to the first option initially: open the default tab on entry, while allowing normal route navigation between tabs.

### Proposed navigation hierarchy

| Sidebar destination | Main-area tabs                                                           |
| ------------------- | ------------------------------------------------------------------------ |
| Overview            | Dashboard, depending on role                                             |
| People              | Athletes · Teams                                                         |
| Testing             | Sessions · Protocols · Devices · Sync Center                             |
| Analysis            | Results · Performance · Trends · Comparisons · Biomechanics · Dashboards |
| Reports             | Report Library · Generated Reports, if supported                         |
| Data & Integrations | Data Sources · Integrations · Datasets, where appropriate                |
| Settings            | Organization · Users · Roles · Preferences                               |

The tabs should change with the selected primary destination. You don't need to display all possible tabs on every page.

### Keep detail-level tabs separate

For example, when a user opens a testing session, the session becomes the context. Its tabs might be:

`Overview` · `Trials` · `Metrics` · `Visualization` · `Analysis` · `Reports`

More technical functions such as raw-data inspection, processing diagnostics, and data quality should appear only when relevant and authorized.

This gives KWinHub three distinct levels without putting all three into the sidebar:

- Sidebar: move between product areas.
- Area tabs: switch between related functions.
- Detail tabs: inspect one specific athlete, session, or result.

## Three implementation decisions I recommend

1. Make tabs route-aware. Each tab should have a real URL or route, so refresh, browser Back/Forward, bookmarks, and access checks behave correctly.
2. Use permissions to filter both levels. A user should not see tabs or sidebar destinations they cannot access, and the API/backend must still enforce authorization.
3. Don't create tabs just to shorten the sidebar. Group features by a meaningful workflow. If a tab contains a very different task or a complicated multi-step process, it may deserve its own primary destination.

One additional point: I would keep Platform Console distinct from the customer-facing KWinHub Web. Its primary destinations should be platform operations—Dashboard, Organizations, Users, Scientific Catalogs, and Security—with tabs inside areas such as Scientific Catalogs for Protocols, Metrics, Devices, and Algorithms.

My conclusion: your proposed sidebar-plus-tabs design is consistent with the navigation pattern documented in VALD Hub. I would use it as the foundation for both KWinHub applications, rather than copying VALD's labels or attempting to reproduce its interface pixel-for-pixel.
