## 6. Important implementation details

1. Use ASP.NET Core Identity or a trusted identity provider for password handling and account lifecycle. Do not implement password hashing or token security from scratch.
2. Keep email sending server-side. Use your transactional email provider, and use a local email capture tool in development.
3. Make registration idempotent where appropriate. Handle duplicate submissions, email collisions, expired verification tokens, and repeated approval requests safely.
4. Validate every privileged API on the backend. Hiding the Platform Console menu is not authorization.

## 3. Recommended data model

Instead of building a separate `IndividualAccount` tenant model, use an organization entity with a type field.

```
Organization
├── Id
├── Name
├── Type              // Standard | Individual
├── Status            // Active | Suspended

├── CreatedAt
└── CreatedByUserId

User
├── Id

└── Status

OrganizationMembership
├── OrganizationId
├── UserId
├── Role              // OrganizationAdmin | Member
└── Status
```

For an individual registration, the backend creates:

1. A user account.
2. An organization with `Type = Individual`.
3. An `OrganizationMembership` record granting the user `OrganizationAdmin` in that personal workspace.
4. An email-verification request.

For a standard organization, it creates the same core records, except the organization type and submitted organization details differ.

### Why this structure works

- Existing tenant-scoped APIs can work for both individuals and organizations.
- Every session and result still has a clear `OrganizationId`.
- An individual can later join a sports club through another membership without converting their personal workspace into a standard organization.
- You avoid maintaining two parallel sets of data-access rules.

One caveat: if individuals should eventually share data with organizations, use explicit membership and resource-sharing permissions. Do not automatically expose personal workspace data when someone joins an organization.

## 1. Why a separate frontend makes sense

Different users and workflows

The KWinHub application serves coaches, sports scientists, athletes, and lab operators. The Platform Console serves platform administrators managing organizations, accounts, global catalogs, and system operations.

A clearer security boundary

The console can have its own routing, navigation, build, and deployment permissions. This reduces accidental exposure of administrative UI, although backend authorization remains the actual security boundary.

Independent evolution

## 4. Security architecture

A separate frontend does not, by itself, secure the platform. I recommend the following controls:

- Dedicated platform authorization: require a server-validated `PlatformAdmin` permission for every administrative API operation.
- Separate application routes and deployment: deploy the Console independently if practical, and optionally restrict access through an identity provider, VPN, or other access policy as your operational requirements mature.
- Least privilege: distinguish platform administrators from organization administrators. Do not grant access to all tenant data simply because a user can access the Console.
- Audit logging: record approvals, suspensions, role changes, catalog publication, and other privileged actions.
- Secure session handling: use an appropriate OAuth/OIDC or session design. If the two apps share an identity provider, define redirect URIs, audiences, scopes, cookie boundaries, and logout behavior deliberately.
- Backend tenant isolation: continue validating `OrganizationId` and access permissions in all organization-facing APIs.

For the MVP, one backend and one identity system are sufficient. You do not need microservices or a separate authentication server solely because there are two frontends.
