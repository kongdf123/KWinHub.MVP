# KWinHub MVP: recommended next changes

I reviewed the current `main` branch of [KWinHub.MVP](https://github.com/kongdf123/KWinHub.MVP?utm_source=chatgpt.com), including the backend projects, `KWinHub.Web.React`, the second frontend, and the updated product/workflow documentation.

My main recommendation is to turn the existing React prototype into one working end-to-end vertical slice, rather than trying to make every page fully functional at once.

Your prototype already has broad UI coverage: athletes, sessions, protocols, results, comparisons, reports, data sources, sync operations, and organization administration. The largest gap is connecting that experience to real backend behavior.

The product requirements define a good MVP target: create an athlete, conduct a test through an existing Kunwei client, synchronize the data, review the result, compare historical measurements, and export a basic report. The workflow specification also explicitly allows simulated ingestion and integrations in the initial prototype. That means you can demonstrate the full workflow without implementing every device integration or the complete production platform.

## 1. Current state: what to keep and what to change

Keep the backend's layered structure

The API, Application, Domain, Contracts, Infrastructure, and Workers projects provide a reasonable foundation. Keep these boundaries instead of rewriting the backend into a single project.

Keep the React UI and demo data as a prototype asset

The React project already has extensive pages and a service layer that simulates asynchronous operations. Reuse the UI and replace the mock data path incrementally.

Connect the React pages to real services

`src/lib/services.ts` explicitly implements a mock-repository pattern, and pages such as `SessionsPage.tsx` and `HomePage.tsx` import demo data directly. A service abstraction alone does not make the UI backend-connected.

Expand the backend beyond subjects

The current API controllers include subject management and development token issuance. The domain and EF Core model already include protocols, measurement sessions, results, and metrics, but these are not yet exposed as a comparable set of end-to-end application workflows.

One positive change compared with the earlier review: the current `SubjectsController` uses `[Authorize]`, and subject reads are scoped by the organization in the current-user context. `Program.cs` also registers JWT authentication and calls `UseAuthentication()` before `UseAuthorization()`. These are meaningful improvements, but they do not establish that tenant isolation and authorization are complete across the whole platform.

## 2. Backend: what I would implement first

The backend should support one complete business workflow, with PostgreSQL as the source of truth. I would not implement all the UI modules' corresponding APIs immediately.

### Priority P0 — Make the core data workflow real

Suggested scope: first implementation milestone

| Area                 | Changes to make                                                                                     | Acceptance criteria                                                        |
| -------------------- | --------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Subjects / athletes  | Extend the existing subject API with update, archive, search, and pagination as needed              | Create an athlete in the UI, refresh, and see the same record from the API |
| Protocols            | Add list/detail endpoints and a small set of seeded test protocols                                  | A session can select a real protocol ID and version                        |
| Measurement sessions | Add create, list, detail, and status endpoints                                                      | Sessions are persisted and scoped to the current organization              |
| Results and metrics  | Add result retrieval and persist structured metrics, units, and trial-level values                  | A completed session can display persisted results                          |
| Development data     | Seed a deterministic demo organization, user/membership, subjects, protocols, sessions, and results | Every developer can start with a predictable dataset                       |
| Database             | Add a documented migration and startup procedure                                                    | A clean PostgreSQL database can be initialized and used reliably           |

The domain model already contains `Subject`, `Protocol`, `MeasurementSession`, `Result`, and `Metric`; `KWinHubDbContext` maps these to PostgreSQL tables. The next step is to make the application layer and API controllers cover the minimum workflow, rather than introducing new domain concepts prematurely.

Recommended initial API surface:

```
GET    /api/v1/subjects
POST   /api/v1/subjects
GET    /api/v1/subjects/{id}
PATCH  /api/v1/subjects/{id}

GET    /api/v1/protocols
GET    /api/v1/protocols/{id}

POST   /api/v1/sessions
GET    /api/v1/sessions
GET    /api/v1/sessions/{id}
GET    /api/v1/sessions/{id}/status

GET    /api/v1/sessions/{id}/results
GET    /api/v1/results/{id}
```

These are proposed endpoints, not a claim that they already exist. Align their names and response schemas with the existing [REST API specification](https://github.com/kongdf123/KWinHub.MVP/blob/main/docs/api/rest-api-and-openapi-specification.md?utm_source=chatgpt.com) before implementing them. For the prototype, you can omit update/delete operations on entities that the first workflow does not need.

### Priority P0 — Simulate ingestion, but persist the outcome

Your [workflow specification](https://github.com/kongdf123/KWinHub.MVP/blob/main/docs/product/workflow-specification-and-prototype-requirements.md?utm_source=chatgpt.com) explicitly permits simulated ingestion and exception handling for the prototype. Use that to keep scope manageable.

A good first implementation would be:

1\. Existing Kunwei client or demo uploader

Submit athlete, protocol, test time, trials and metrics

2\. KWinHub API

Authenticate · validate · deduplicate · save session

3\. Simulated processing

Set processing status and produce deterministic test results

4\. React application

Show status, results, history and comparison

For the first version, the processing can be synchronous or handled by a simple background worker. If you retain asynchronous ingestion, implement the actual state transitions rather than merely returning a simulated `202 Accepted` response.

At minimum, support a lifecycle such as:

`RECEIVED → VALIDATING → PROCESSING → ANALYZED`

with explicit failure states and a way to retry a failed operation. Persist the state in PostgreSQL so it survives a refresh or server restart.

Two details are especially important:

- Idempotency: a client retry must not create duplicate sessions or results. Persist the idempotency key with a unique constraint scoped appropriately to the organization or integration.
- Reproducible demo results: use deterministic fixture data or a fixed test calculation. Do not generate random values on each request, because that makes result comparison and debugging unreliable.

The existing `KWinHub.Workers/Worker.cs` is currently a logging loop. Do not turn it into a large job-processing framework yet. Either use a simple application service for the first demonstrator or give the worker one clearly defined responsibility, such as transitioning queued sessions through simulated processing.

### Priority P0 — Complete the authorization boundary

The current subject endpoints are a good start, but the security rule must apply to every tenant-owned resource.

1. Keep JWT authentication and `[Authorize]` on protected endpoints.
2. Resolve the organization from a validated user context; do not trust a caller-supplied organization header as proof of membership.
3. Verify active organization membership and the required role for the operation.
4. Scope queries for protocols, sessions, results, metrics, files, and exports to the authorized organization.
5. Fail closed if user or organization claims are missing or invalid. Returning `Guid.Empty` from `CurrentUserContext` should not silently become an alternative tenant identity.
6. Keep `DevAuthController` available only in Development. Its ability to issue a token for a supplied organization and role is suitable only for controlled local testing, not a production login flow.
7. Add cross-organization tests before adding more endpoints.

For the prototype, a development token issuer and seeded demo account are reasonable. A full production identity provider can be a separate milestone, but tenant isolation must be implemented and tested from the beginning.

### Priority P1 — Defer infrastructure that does not prove the workflow

Do not make these prerequisites for the first working vertical slice:

- Microservices or a message broker.
- Distributed caching.
- A general-purpose workflow engine.
- A full device-vendor plugin system.
- Advanced analytics pipelines.
- Every device, integration and admin API.
- Complex permissions configuration UI.

The existing project layering is sufficient. Implement the simplest maintainable solution that respects the existing contracts and can later be extended.

### Change 1 — Introduce one real API client

The current `services.ts` documents the intended separation between UI and data access, but the pages still import demo data directly. That means switching the service implementation alone will not make all pages use the backend.

Create a small API layer, for example:

```
src/lib/
├── api/
│   ├── http.ts
│   ├── subjects-api.ts
│   ├── protocols-api.ts
│   ├── sessions-api.ts
│   └── results-api.ts
├── services/
│   ├── subjects-service.ts
│   ├── sessions-service.ts
│   └── results-service.ts
├── demo-data.ts
├── types.ts
└── app-context.tsx
```

This is a proposed structure; you can retain the current `services.ts` and split it only as the implementation grows.

The API client should centralize:

- API base URL from `VITE_API_BASE_URL`.
- Bearer token attachment.
- JSON serialization and response parsing.
- Consistent handling of `400`, `401`, `403`, `404`, and `500` responses.
- Network errors, loading states and cancellation where appropriate.
- Request correlation IDs if the backend exposes them.

For example, configure the local environment using:

```
VITE_API_BASE_URL=https://localhost:7001/api/v1
```

Use the actual API URL and port from your local launch configuration. Do not commit real credentials or signing keys into frontend environment files.

### Change 2 — Keep mock mode, but make the switch explicit

I would not delete `demo-data.ts`. It is useful for visual development and for screens that are not yet connected to the backend.

Instead, introduce an explicit data-provider selection:

```
UI component
    ↓
Domain service
    ↓
┌────────────────────┐
│ API provider       │  → KWinHub backend
│ Demo provider      │  → deterministic fixtures
└────────────────────┘
```

For example:

```
type DataMode = 'demo' | 'api';
```

Use an environment setting or a development-only configuration to select the provider. Keep the same service interface for both implementations.

Important rules:

- A page must not combine live API data with unrelated mock records without explicitly labeling the difference.
- In API mode, an API failure should show an error and retry action. It should not silently fall back to demo data, because that could make users believe unsaved or stale information is real.
- Demo mode should visibly indicate that the data is simulated.
- Use stable demo IDs so related athletes, sessions and results stay linked.

### Change 3 — Replace fake login with the correct prototype authentication flow

In [`App.tsx`](https://github.com/kongdf123/KWinHub.MVP/blob/main/src/frontend/KWinHub.Web.React/src/App.tsx?utm_source=chatgpt.com), the application currently uses local `loggedIn` state. The [`LoginPage.tsx`](https://github.com/kongdf123/KWinHub.MVP/blob/main/src/frontend/KWinHub.Web.React/src/pages/LoginPage.tsx?utm_source=chatgpt.com) simulates login with a timeout; it does not authenticate against the backend.

For a development prototype:

1. Add a Demo sign-in action.
2. Call the backend's development token endpoint in Development.
3. Retain the access token in memory where practical, or use an appropriately scoped short-lived session for local testing.
4. Attach the token to API requests.
5. On `401`, clear the session and return to the login screen.
6. On `403`, show a permission error rather than treating it as an expired login.

Avoid adding a home-grown production login/password system. Replace development token issuance with a proper OIDC/OAuth flow before real users or sensitive data are introduced.

### Change 4 — Convert the most valuable pages first

Do not refactor all 25-plus views at once. Prioritize the pages that establish the business workflow.

1\. `AthletesPage.tsx` and `AthleteProfilePage.tsx`

Replace direct demo-data access with the subjects API. Implement create, view, search and edit for the first demonstrator.

Outcome: a real athlete record can be created and revisited.

2\. `ProtocolsPage.tsx` and `ProtocolDetailPage.tsx`

Read the available protocols from the backend. Use a small, seeded protocol catalogue initially.

Outcome: the session workflow uses stable protocol IDs and versions.

3\. `SessionsPage.tsx` and `SessionDetailPage.tsx`

Connect list, detail, creation and status polling. Keep the existing status badges, filters and layout where possible.

Outcome: users can track a real persisted session from submission to completion.

4\. `ResultsPage.tsx`, `ResultDetailPage.tsx`, and `ComparisonsPage.tsx`

Read stored results and compare values from two or more sessions using the same metric definition and unit.

Outcome: users can inspect real API-backed results and historical changes.

5\. `ReportsPage.tsx`

Add a basic report/export for the pilot workflow after the result model stabilizes. A CSV or printable HTML report is enough to start.

Outcome: the first workflow produces a useful deliverable.

Leave advanced dashboards, integrations, sync-center controls, device management, and sophisticated biomechanics visualizations in demo mode until their backend contracts are ready. Do not imply that the prototype can control physical devices if it only displays simulated device status.

### Change 5 — Make the UI reliable when data comes from a server

Mock data is always available and arrives predictably. Real APIs introduce latency, empty results and failure conditions. Add the following to the core pages:

- Loading skeletons or indicators.
- Explicit empty states.
- Error messages with a retry action.
- Form validation and server validation errors.
- Disabled submit buttons while a mutation is in progress.
- Confirmation for destructive actions.
- A refresh strategy for session status.
- Clear timestamps and units for measurements.

You do not need to introduce a large state-management library immediately. React hooks and the existing application context can support the first slice. If the number of queries and mutations grows substantially, consider a server-state library such as TanStack Query.

### Change 6 — Decide what to do with the second frontend

The repository also contains `src/frontend/KWinHub.Web`, a Vue implementation with its own API code. Its current subject API sends an `X-Organization-Id` header, whereas the current React backend flow resolves organization context from token claims. That mismatch should be resolved rather than allowing two frontends to evolve against different authentication assumptions.

For the MVP:

- Recommended: use React as the primary prototype and mark Vue as experimental or legacy until a deliberate decision is made.
- If Vue is still intended to be a production frontend, bring its API client and authentication model into alignment with the backend before using it for demos.
- Avoid implementing the same business feature twice in both frontends.

The purpose is not to prove that React is universally better than Vue. It is to concentrate the limited MVP effort on one coherent user experience.

## 4. Testing and deployment: the minimum needed for a credible prototype

The repository has unit, contract, integration and end-to-end test projects, but the checked-in integration, contract and end-to-end projects contain placeholder tests. Their presence should not be mistaken for workflow coverage.

I would add these tests first:

| Test                   | What it should prove                                                |
| ---------------------- | ------------------------------------------------------------------- |
| Backend unit tests     | Subject and session validation, status transitions, metric handling |
| API integration tests  | Authenticated requests work against a test database                 |
| Tenant isolation tests | Organization A cannot read or modify Organization B's records       |
| Idempotency tests      | Repeated ingestion with the same key does not duplicate a session   |
| React service tests    | API responses, loading, error and empty states behave correctly     |
| End-to-end test        | Create athlete → create session → process → view result             |

For the first end-to-end test, use deterministic seed data and simulated processing. There is no need to connect a real force plate or video device to validate the platform's data lifecycle.

I would also make sure the team can start the backend and frontend with documented steps, initialize a clean PostgreSQL database, and run the automated checks in CI. Your existing Docker Compose setup can remain the local development foundation; production deployment automation can follow after the core workflow is stable.

## Final recommendation

Keep the architecture you have, but narrow the implementation to one organization, one real athlete workflow, one protocol, one ingestion path, and persisted results. The React application should be the main interface for that workflow; demo data should remain a deliberate development mode rather than an invisible substitute for the backend.

Once that path works reliably, you will have a much stronger foundation for integrating real Kunwei desktop/mobile applications, devices, raw measurement files, and more advanced sports-science analysis.

Design rules worth establishing now
Stable identity: Map client-side athlete and session IDs to KWinHub IDs explicitly.

Idempotency: Retrying the same submission must not create duplicate sessions or results.

Units and semantics: Store units and metric definitions; don't silently convert or reinterpret values.

Raw versus derived data: Preserve raw samples when needed for reanalysis, but don't require high-frequency raw data in the first API if the client can provide validated summary metrics.

Tenant isolation: Derive organization access from authenticated claims and membership, not a client-supplied organization ID.

Auditability: Keep the source client, device metadata, timestamps, and processing outcome.

3. Define the canonical data contract
I suggest separating each completed test into three logical records.

Record

Purpose

Core fields

Session

Identifies the test event

Subject, protocol, start/end time, source client, device

Raw measurement

Preserves the original signal

Sample rate, channel definitions, timestamps, values, units

Metric result

Stores calculated outcomes

Metric code, value, unit, calculation source, algorithm version

For example, a countermovement jump (CMJ) session could contain force samples over time plus summary metrics such as peak force or jump height. The exact fields and calculations must be verified against the actual Kunwei client output.

Important data-model decisions
Raw data: Keep it separate from ordinary session metadata. For large time-series payloads, consider object/file storage with metadata and a checksum in PostgreSQL rather than storing every sample in a large JSON column.

Summary metrics: Persist each metric with its unit, metric definition, and provenance. Distinguish values calculated by the client from values calculated by KWinHub.

Protocol versioning: Record the protocol and calculation version used for a test. A metric can change meaning when its calculation algorithm changes.

Data integrity: Validate sample count, timestamps, channel names, units, and payload size. Preserve the original uploaded artifact when practical and permitted.

Idempotency: Use a stable external session ID and an idempotency key so a timeout and retry cannot create duplicate results.

The ingestion endpoint can accept session metadata, summary metrics, and either inline raw samples or a reference to an uploaded raw-data artifact. For large recordings, a separate upload flow is preferable.

For local database integration, the adapter should read the client data and transform it into the same canonical contract; it should not bypass KWinHub's authorization, validation, or persistence rules.

4. Implementation plan for the existing KWinHub MVP
I would divide the work into four milestones.

Milestone 1 — Contract and fixtures

Define the force plate JSON schema, metric naming and unit conventions, and sample data. Create representative success, invalid-data, and duplicate-submission fixtures.

Milestone 2 — Backend ingestion

Milestone 4 — Additional adapters

Add JSON/CSV import and the specific local database/service adapter, both using the same canonical ingestion pipeline. Test that the same source test produces equivalent stored results regardless of its entry method.

3. Upload protocol: reliable online and offline sync
For recordings of 1–20 MB, I would start with a three-step upload protocol, with retries and checksum validation. Whole-file uploads are usually sufficient at this size; add chunk-level resumability only if testing shows that network interruptions make retries too expensive.

Proposed flow
1
Create an ingestion

POST /api/v1/ingestions

Send the external session ID, subject mapping, protocol, recording metadata, file size, checksum, and client version.

The Hub creates an ingestion ID and returns the next upload action.

2
Upload the raw file

PUT /api/v1/ingestions/{id}/raw-data

Upload the binary payload. Validate file size and SHA-256 checksum before marking the artifact as complete. For object storage, the API can instead issue a short-lived, scoped upload URL.

3
Finalize and process

POST /api/v1/ingestions/{id}/complete

Verify the artifact, validate the measurements, persist client metrics, and enqueue or start recalculation. Return a durable processing status.

These are proposed endpoints. The implementation should align with the repository's existing REST conventions.

Important retry behavior
The client generates a stable external session ID before attempting upload.

A retry of the same test returns the existing ingestion rather than creating another one.

The Hub verifies the checksum and recognizes an already uploaded identical artifact.

An incomplete upload is not treated as a completed measurement.

If the server accepts the data but the acknowledgement is lost, the client can query the ingestion status instead of resubmitting a new test.

A processing failure does not require uploading the raw file again unless the artifact itself is invalid or missing.

For 20 MB recordings, test ordinary upload and retry behavior first. If a recording takes a long time to upload over unreliable connections, introduce a resumable upload session with chunk offsets, per-chunk checksums, and explicit finalization.

4. Offline-first client design
The client should save a completed measurement locally before attempting network transmission. This prevents a Hub outage or disconnected network from losing test data.

Use a local durable queue with these states:

Captured locally

Queued for sync

Uploading

Hub accepted

Retry later

Implementation rules:

Store the raw recording and queue metadata in a durable local location, with the external session ID and checksum.

Retry transient network errors with exponential backoff and jitter; do not retry permanent validation errors indefinitely.

Keep the queued file until the Hub has durably accepted the artifact. If the Hub's acceptance and the client acknowledgement become ambiguous, query status first.

Show local sync state in the client: Pending, Uploading, Synced, or Needs attention.

Support multiple pending tests and restart recovery.

Avoid automatic deletion of local recordings until the retention and recovery policy is clear.

An important distinction: uploaded does not mean analyzed. The Hub may have the original file safely stored while recalculation is still running or has failed.

5. Recalculation architecture
Because recalculation is required in the MVP, make the analysis pipeline an explicit backend capability rather than a side effect hidden inside the upload endpoint.

Recommended processing sequence
1
Artifact verified

Checksum and file format validated

2
Signal validated

Channels, sample rate, units and timestamps checked

3
Analysis executed

Versioned algorithm computes metrics

4
Results persisted

Metrics and provenance saved transactionally

5
Session completed

Status exposed to React

Separate client and Hub calculations
Store both sources of metrics, for example:

Client result: the value originally calculated by the force plate client.

Hub result: the value calculated from the preserved raw signal by the KWinHub analysis implementation.

Each calculated result should carry:

Metric code and unit.

Algorithm name and version.

Input artifact ID and checksum.

Processing timestamp and status.

Any relevant parameters or calibration references.

Do not overwrite client metrics with Hub metrics. They may legitimately differ because of filtering, event detection, calibration, or algorithm-version differences.

Also, do not invent or approximate the force plate algorithms. For the first protocol, verify the mathematical definitions, signal-processing parameters, units, and expected output against Kunwei's current implementation and validated test recordings. Add reference datasets with expected results as regression tests.

For the MVP, a database-backed job table and a simple worker are enough. Make jobs idempotent and recoverable after a process restart; introduce a message broker later only if workload or throughput justifies it.

The work should proceed in the following order.

P0 — Storage and domain model

Separate client-reported metrics from versioned Hub-calculated metrics.

Add migration and development seed data.

Implement IRawDataStorage and a local or S3-compatible provider.

Enforce tenant-scoped access and private artifact access.

P0 — Ingestion API

Implement create, upload, complete, and status endpoints.

Add idempotency constraints and checksum verification.

Validate payload sizes, metadata, and file formats.

Add explicit failure states and safe retry behavior.

Ensure incomplete uploads cannot appear as completed sessions.

P0 — Analysis pipeline

Define a versioned raw-signal input format.

Port or implement one verified force plate analysis protocol.

Persist original and recalculated metrics separately.

Add job recovery and deterministic regression tests.

Expose processing status and analysis errors.

P0 — Client sync and React

Persist a local outbox and retry policy in the desktop client.

Implement a sync worker that recovers pending uploads after restart.

Connect React session lists, result details, and status polling to live APIs.

Display upload status separately from analysis status.

Keep demo mode explicit; do not silently show mock data after an API error.

P1 — Reliability and validation

Test interrupted uploads and reconnection.

Test duplicate submissions and lost acknowledgements.

Test cross-tenant access, expired credentials, and malformed files.

Compare Hub metrics against known-good client outputs.

Verify backup and recovery of raw artifacts and metadata.

The integration is ready for demonstration when all of the following are true:

Final recommendation
For the first release, use PostgreSQL + S3-compatible raw-data storage + a durable local client outbox + a versioned analysis worker. Implement whole-file uploads with checksums and retry-safe ingestion first; add chunked uploads only if real connectivity tests justify the extra complexity.

The main dependency is not the upload mechanism. It is obtaining a validated raw-data schema and a reproducible implementation of one Kunwei force plate protocol. Confirm those two pieces early, and the rest of the MVP can be developed against fixtures in parallel.
